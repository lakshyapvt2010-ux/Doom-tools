1. Executive summary
Agentic Tools is a modular, TypeScript-first toolkit for developers building AI agents and agentic
applications. It provides reusable tools (for example, Bash, filesystem, Git, web, browser and
database operations), a unified tool contract, a policy-aware execution runtime, and adapters that
expose the same tool implementations to different agent frameworks and MCP environments.
The product addresses fragmented tool implementation: developers repeatedly build or adapt the
same capabilities, wire different schema formats, handle execution errors, and independently
implement permissions, sandboxing, audit logs and resource limits. Agentic Tools aims to make
those foundations reusable and safer by default.
The tool catalogue (Appendix A) is intentionally broad. It represents the potential ecosystem, not
a commitment to ship every integration in the first release. The recommended initial release is

developer-first and local-runtime-first, with interfaces designed to support remote execution
later. A hybrid local/remote product direction is a strategic hypothesis to validate.
Differentiation wedge. MCP already standardizes how tools are exposed to clients, so Agentic
Tools does not compete on protocol translation. Its differentiation is the policy-aware execution
runtime (permissions, approvals, isolation options, redaction, audit and output limits) that sits
beneath whichever protocol or framework exposes the tools. The MCP server is therefore the
primary distribution surface and ships in P0; framework adapters are thin and follow. This is a
hypothesis, to be validated by the go/no-go gate in section 20 before the P0 build is committed.

2. Product vision and positioning
2.1 Vision
Become the reusable capability and execution layer developers reach for when giving AI agents
access to tools, data, software projects and external systems.

2.2 Positioning
A framework-independent tool ecosystem with a consistent developer experience and a securityaware runtime. It is not an LLM, an agent orchestrator, or a replacement for LangGraph, Vercel AI
SDK, OpenAI Agents SDK or MCP. It supplies capabilities those systems can invoke.

2.3 Product promise
Build once: implement a tool against one canonical contract.
Connect anywhere: adapt tools to supported frameworks and MCP.
Execute consistently: apply policies, limits, tracing and error handling centrally.
Compose freely: install only the tool packages needed and define custom tools with the
same SDK.

2.4 Relationship to MCP and the differentiation wedge
MCP standardizes how tools are described and exposed to clients, and many frameworks and
clients already consume it. Agentic Tools therefore does not compete on protocol translation. The
wedge is the layer a protocol leaves to implementers: a consistent execution runtime with
capability-based permissions, approvals, isolation options, redaction, audit and output limits,
applied identically whichever protocol or framework exposes the tools.
Consequences for the product:
1. The MCP server is the primary distribution surface and ships in P0; framework adapters are
thin and follow.
2. The runtime must be valuable on its own, including when wrapping tools it did not write
(for example external MCP servers; see section 20).
3. Built-in tools are justified where owning the implementation is necessary to enforce policy
(filesystem, shell, Git). Commodity tools should integrate existing libraries.
This wedge is a hypothesis. Section 20 defines the gate that must be passed before the P0 build is
committed.

3. Problem statement
Developers building agents commonly need tools such as shell execution, file operations, Git,
browser automation, search, HTTP, databases, memory and cloud services. These capabilities are
scattered across libraries, framework-specific examples and custom code. Tool schemas, return
formats and error semantics differ. Security controls are frequently implemented inconsistently
or left to application code. Reusing a tool in a second framework can require rewriting its wrapper.
This creates six main problems:
1. Reimplementation: common tools are repeatedly written for individual projects.
2. Fragmented interfaces: each framework/provider expects different schemas and
invocation patterns.
3. Unsafe execution: shell, filesystem, browser and cloud actions can cause real-world
damage without isolation and permissions.
4. Poor operability: timeouts, retries, tracing, audit logs and output limits are handled
inconsistently.
5. Integration overhead: developers must discover, configure and maintain many separate
packages.
6. Context and selection cost: exposing every available tool inflates the model's context and
degrades tool selection. Developers need to expose only the tools and operations an agent
actually needs, and to vary that per task.

4. Goals and non-goals
4.1 Goals
Provide a canonical, strongly typed tool interface and stable execution contract.
Ship a curated library of commonly used agent tools as modular packages.
Make local execution safe by default through explicit permissions, bounded execution and
isolation options.
Support adapters for multiple agent frameworks without duplicating tool logic.
Support MCP as both a client connection mechanism and a way to expose local tools.
Make custom tool creation simple.
Provide tracing, structured errors, metrics and audit events across tools.
Keep provider credentials and secrets outside model-visible tool outputs and logs.
Make the runtime extensible toward remote sandbox execution.
Let developers expose only the tools and operations an agent needs, selectable per toolkit,
per run and per MCP server, with the selection enforced by the runtime.
Return model-friendly results: bounded, paginated and deterministically truncated outputs
with explicit truncation markers.

4.2 Non-goals for the initial release
Building a new agent orchestration framework or LLM provider.
Training, hosting or fine-tuning foundation models.
Providing a hosted remote execution service at MVP launch.
Shipping every tool in the catalogue at launch.

Guaranteeing that arbitrary shell commands or third-party browser workflows are safe.
Replacing dedicated vendor SDKs, database clients, cloud CLIs or framework-native tools.
Making domain-specific decisions in regulated areas (finance, healthcare or legal).
Windows support for execution tools (shell, process) in the initial release; macOS and Linux
come first.
Any claim of containment for host-mode shell execution; the initial release offers trustedhost shell only.

6. Product principles
1. Security is part of the execution contract. Tools do not bypass the runtime policy layer.
2. Framework neutrality. The canonical tool implementation is independent of any LLM or
agent framework.
3. Least privilege. A tool receives only the resources and permissions it needs.
4. Explicit side effects. Read-only, mutating, destructive and external actions are declared.
5. Composable by default. Tools, adapters and runtime backends are independently
installable.
6. Observable by default. Every invocation has traceable identity, timing, status and policy
outcome.
7. Predictable outputs. Structured results and errors are preferred over unbounded text.

8. Honest capability boundaries. A local process wrapper is not called a sandbox unless OSlevel isolation is actually used.
9. Selective exposure. The model sees only the tools and operations explicitly selected for
that toolkit, run or server. Installing a package does not expose everything in it, and hiding a
schema is never the only control.

7. Core product experience
7.1 Desired developer experience
Install the core and only the tool/adapters needed. Configure a workspace, permissions and
runtime. Create a toolkit and export it to a supported framework or start an MCP server.
bash

pnpm add @agentic-tools/core @agentic-tools/runtime
pnpm add @agentic-tools/bash @agentic-tools/filesystem @agentic-tools/git
pnpm add @agentic-tools/adapter-mcp @agentic-tools/adapter-vercel

ts

import { createToolkit } from "@agentic-tools/core";
import { bash } from "@agentic-tools/bash";
import { filesystem } from "@agentic-tools/filesystem";
import { git } from "@agentic-tools/git";
const toolkit = createToolkit({
// One source of truth for the boundary. Tools inherit it; a tool-level
// root may only narrow it.
workspace: "./workspace",
// Operation-level selection. Omitting `only` applies the package's
// read-only default set; write operations must be listed explicitly.
tools: [
filesystem({ only: ["read", "list", "search", "grep"] }),
git({ only: ["status", "diff", "log"] }),
bash({ mode: "trusted-host" }) // explicit opt-in; not a sandbox
],
runtime: { backend: "local" },
policy: {
filesystem: "workspace-only",
network: "deny-by-default", // applies to runtime-mediated tools only
approvals: { "process.execute": "always", "filesystem.write": "ask" }
}
});
// Run-level narrowing, enforced by the runtime (read-only tools only)
const planning = toolkit.select({ sideEffect: ["read"] });
// Expose through MCP (primary) or a framework adapter
await planning.serveMcp({ transport: "stdio" });
const frameworkTools = toolkit.toVercelAI();

The example is illustrative. Exact adapter method names and framework compatibility must be
finalized against the versions supported at release. A toolkit must fail closed when a required
policy or runtime capability is unavailable. API names are illustrative.
Design notes for the example:
One source of truth. Tools inherit the workspace root from policy rather than declaring
their own; a tool-level root may only narrow it.
Selection. only chooses operations within a package. The default set is minimal and readonly; write, external and destructive operations must be listed explicitly (section 8.6).

Honest shell mode. Bash runs in trusted-host mode: host privileges, explicit opt-in,
approval-gated by default. It is not a sandbox, and no "restricted" mode is offered in P0.
Network policy scope. network governs runtime-mediated tools (HTTP, web fetch) and
sandboxed backends. It cannot be enforced for host-mode shell, and the CLI must say so
when such a configuration is loaded.

7.2 User flows
Install: add core, runtime, tool packages and optional adapter.
Configure: define workspace roots, allowed operations, network policy, timeouts and
resource caps.
Compose: register built-in and custom tools.
Select: choose which tools and operations are visible to the model, per toolkit, per run and
per MCP server (section 8.6).
Expose: convert tools into framework-specific definitions or run an MCP server.
Execute: validate, authorize, approve if needed, execute in the selected backend, sanitize
and return results.
Inspect: view traces, structured errors, execution history and audit events.

8.3 Canonical tool contract
Each tool must declare a stable name, description, version, input schema, output contract, sideeffect classification, required capabilities, risk metadata and an execution function. JSON Schema
is the canonical interchange format (proposed; confirm in the prototype). defineTool accepts
either raw JSON Schema with inferred TypeScript types, or a Zod schema that is converted to
JSON Schema at registration. Both produce the same ToolDefinition , and Zod is never the only
wire format.
ts

type SideEffect = "read" | "write" | "external" | "destructive";
type Risk = "low" | "medium" | "high";
interface ToolDefinition<TInput, TOutput> {
name: string;
description: string;
version: string;
inputSchema: JSONSchema;
outputSchema?: JSONSchema;
sideEffect: SideEffect;
// static upper bound for the tool
capabilities: string[];
// static set of capabilities the tool may
request
risk: Risk;
// static default
// Optional: refine side effect, risk and capabilities for one concrete
input.
classify?(input: TInput): InvocationClass;
execute(input: TInput, context: ToolContext): Promise<ToolResult<TOutput>>;
}
interface InvocationClass {
sideEffect: SideEffect;
risk: Risk;
capabilities: CapabilityRequest[]; // e.g. { name: "filesystem.write",
path: "<resolved path>" }
}

Static metadata is an upper bound; classification refines it per call. Tools whose risk depends
on their arguments (shell, SQL, HTTP, browser, cloud) must implement classify , which runs
before policy evaluation. A classification may narrow but never exceed the tool's declared

sideEffect and capabilities . If classification throws or is ambiguous, the runtime falls back

to the static upper bound (fail closed). Classification is an input to policy, not a guarantee: the
runtime cannot reliably infer the intent of an arbitrary shell command, so shell invocations
classify as destructive/high unless they match an explicitly configured named command, and are
therefore approval-gated by default.
ToolContext should provide scoped capabilities, cancellation, trace identifiers, logger, policyapproved resource handles and deadline information. context.services contains only services
that the host application registered ( createToolkit({ services }) ) and whose capabilities the
tool declared and policy granted; accessing any other service fails with permission_denied .

Tools must not receive unrestricted global access by default.

Result envelope. The canonical execute returns a ToolResult . defineTool (section 11) lets
authors return a plain value or throw; the SDK wraps the value in a success envelope or maps the
error to the stable error model. Authors construct a ToolResult explicitly only when they need
warnings or custom metadata.

8.4 Standard result and error model
Every execution returns a structured success or failure envelope with a correlation/trace ID, tool
name/version, status, output, warnings, timing and sanitized metadata. Errors should have stable
codes (validation, permission_denied, approval_required, timeout, cancelled, resource_limit,
not_found, conflict, provider_error, execution_error) and safe messages. Raw secrets, stack traces
and environment values must not be exposed to the model by default. Model-facing output
shaping. Results carry a model-facing rendering alongside the structured payload. Tools and the
runtime apply configurable byte and token budgets (per tool and per toolkit), pagination cursors
for large listings and searches, and deterministic truncation that states what was cut and how to
retrieve more. Truncation must never silently drop content, and oversized results may be
summarized only when the summary is labeled as such.

8.5 Execution lifecycle
1. Discover the tool and validate its registered metadata.
2. Check selection: reject calls to any tool not exposed to this toolkit, run or server
( permission_denied ), even if the registry knows the name.
3. Validate input against the canonical schema.
4. Classify the invocation (static metadata, refined by the tool's classify hook where
declared; fail closed to the static upper bound).
5. Resolve caller identity, task scope and trace context.
6. Evaluate policy and resource access against the classified invocation.
7. Create an approval request where policy requires it and wait for a decision (section 9.5).
8. Select an execution backend and provision scoped resources.
9. Execute with timeout, cancellation and resource limits.
10. Sanitize, shape and bound output.
11. Emit trace, metrics and audit events.
12. Return a structured result through the selected adapter.

8.6 Tool selection and exposure
Installing a package never exposes all of its operations to the model. Exposure is chosen at four
levels, and the runtime enforces it. Method names are illustrative.
Package level: developers install only the packages they need.
Operation level: a package may contain many operations (for example Git status, diff and
commit). Developers choose them with only / except . Each package documents a default
operation set that is minimal and read-only. Write, external and destructive operations are
never in the default set and must be listed explicitly.
Run level: toolkit.select({...}) returns a derived toolkit narrowed by name, tag, side
effect, risk or capability (for example read-only tools during a planning phase). A derived
toolkit shares the parent's runtime, policy and audit stream, and can only narrow, never
widen, what the parent allows.
Server level: MCP server mode exposes only the selected set, and supports per-client
selection where the transport provides client identity.
Enforcement. Hiding a schema is not a security control. The runtime rejects a call to any tool that
is not exposed to the current toolkit, run or server with permission_denied , including names the
model guessed or hallucinated.
Context footprint. The toolkit reports the approximate token cost of the definitions it exposes
(for example toolkit.describeFootprint() and agentic-tools tools list --tokens ), and
package defaults keep descriptions concise. Dynamic tool discovery (deferred loading or tool
search, for frameworks and clients that support it) is a P2 item to evaluate once selection is in
place.

9. Security, privacy and safe execution
Security is a core product requirement, not a later enhancement. Tool descriptions and model
prompts are not security boundaries. All authorization must be enforced by runtime code outside
the model.

9.1 Required controls
Workspace isolation: filesystem tools default to an explicitly configured root; canonicalize
paths and prevent traversal/symlink escapes.
Shell containment: command allowlists, argument filters and "restricted" modes are not a
security boundary; subcommands, flags and wrapper programs that spawn other programs
make them bypassable. P0 shell execution therefore runs in trusted-host mode only: explicit
opt-in, approval-gated by default, with host privileges documented. Untrusted code requires
an OS-level or container sandbox backend (P1).
Network egress: deny by default for isolated execution; allow approved domains or network
profiles when necessary. Egress policy applies to runtime-mediated tools and sandboxed
backends. It cannot be enforced for host-mode shell, and the CLI and docs must say so.
Credential isolation: expose references and operations, not raw secrets. Apply best-effort
redaction of known secret values and patterns in stdout, stderr, traces and errors. Redaction
reduces but cannot eliminate leakage (encoded, transformed or split values can evade it), so
secrets should not be placed in tool-accessible environments in the first place.
Approval gates: require human approval for destructive changes, external writes,
deployments, payments, messages or privilege escalation according to policy.

Resource limits: enforce time, CPU, memory, disk, process count, file size, request size and
output limits where backend supports them.
Auditability: record who/what invoked a tool, policy decision, approval, backend and
outcome, without logging sensitive payloads by default.
Supply-chain safety: pin/verify dependencies, publish provenance where practical, and
document package permissions.
Prompt-injection mitigation: treat web pages, files, tool outputs and MCP server responses
as untrusted data, not instructions to override policies. A runtime cannot solve prompt
injection, but it limits the blast radius by enforcing policy outside the model, labeling
untrusted content in results, and approval-gating sensitive actions. Taint-aware policy
(tightening approvals after untrusted content enters the context) is a P2 research item.

9.2 Permission model
Permissions should be capability-based and scoped. Example capabilities: filesystem.read ,
filesystem.write , process.execute , network.http , git.write , database.read ,
database.mutate , browser.control , cloud.deploy . Policies can bind capabilities to paths,
hosts, repositories, database schemas, accounts and time windows.

9.3 Trust modes
Trusted local (trusted-host): developer-controlled machine; commands run with host
privileges and no containment. This is the only mode for shell execution in P0. It requires
explicit opt-in and is approval-gated by default.
Restricted local: the runtime mediates access and limits operations for tools whose
operations it can fully mediate (filesystem, Git, HTTP). It does not apply to shell execution,
and must clearly disclose what is and is not isolated.
Sandboxed local: OS/container-backed isolation with declared guarantees.
Remote sandbox (future): isolated worker with authenticated control plane, ephemeral
credentials and cleanup guarantees.

9.4 Sensitive actions
Destructive database mutations, shell commands with broad side effects, file deletion outside
disposable workspaces, cloud deployments, secret access, financial transactions, sending
communications and production infrastructure changes must be denied or approval-gated by
default. Policies may be stricter, never silently relaxed by the agent.

9.5 Approval flow
Approval is a cross-cutting runtime feature, not an adapter feature. It must work for interactive
agents, non-interactive agents and MCP clients.
First-class requests. An approval request is a runtime object with an ID, the tool, the
classified invocation, the policy rule that triggered it, a redacted input preview and an
expiry.
Pluggable approvers. An approver interface supports an in-process callback, a CLI prompt,
a webhook or queue for non-interactive and remote agents, and MCP elicitation where the
client supports it.
Pause and resume. The invocation suspends and resumes after a decision. A decision is
bound to the exact classified input, so approving one command never approves another.

Approvals expire, and any "approve always" is scoped narrowly and controlled by policy.
Non-interactive default. If a call requires approval and no approver is available, it fails with
approval_required . It is never auto-approved.
Framework integration. Where a framework has native human-in-the-loop support, the
adapter maps to it. Where it does not, the adapter returns approval_required with a
resumable request ID. No adapter may skip or weaken approval.
Validation. Prototype the approval flow end to end through MCP and one framework before
the P0 scope is locked.

10. Framework and protocol interoperability
10.1 Initial adapters
P0: MCP server exposure (primary distribution surface; stdio transport first) and one
framework adapter, chosen on target-persona usage and API stability.
P1: MCP client connections (external tools registered as untrusted), Streamable HTTP
transport, and additional framework adapters among Vercel AI SDK, LangChain /
LangGraph and OpenAI Agents SDK. The adapter layer translates schemas, tool-call
arguments, streaming events, cancellation and errors. It must not reimplement tool
behavior or weaken runtime policy. Compatibility is versioned and tested in CI against
declared supported versions.

10.2 Adapter acceptance criteria
Same canonical tool can be invoked through each supported adapter.
Input validation and runtime policy behave identically across adapters.
Cancellation and timeouts propagate where framework APIs permit.
Structured errors are converted without losing stable error codes.
Streaming/partial output behavior is explicitly documented.
No adapter can bypass approval, redaction or audit hooks.

10.3 MCP
Support MCP as both a server and a client. Server mode exposes registered tools and, where
appropriate, resources and prompts. Client mode connects to configured external MCP servers.
Server trust, authentication, transport, tool discovery and session lifecycle must be explicit.
Remote MCP tool outputs remain untrusted and are subject to local policy.
MCP clients differ in support for elicitation, tool annotations and structured output, so server
mode must degrade safely: tools that require approval are not exposed to a client that cannot
present an approval unless policy configures an out-of-band approver. Publish an MCP client
compatibility matrix.

11. Extensibility and custom tool SDK
Developers must be able to define custom tools using a typed helper and register them with the
same runtime. A custom tool receives a constrained ToolContext ; it does not automatically
inherit every host permission.

ts

import { defineTool } from "@agentic-tools/core";
export const searchUsers = defineTool({
name: "search_users",
description: "Search users in the application",
inputSchema: {
type: "object",
properties: { query: { type: "string" } },
required: ["query"],
additionalProperties: false
},
sideEffect: "read",
capabilities: ["database.read"],
execute: async ({ query }, ctx) => {
return ctx.services.database.users.search({ query });
}
});

The SDK should provide schema validation, policy checks, tracing, structured errors, adapter
compatibility and a local test harness automatically.
defineTool wraps a returned plain value in a success ToolResult and maps thrown errors to

the stable error model, so the example above needs no explicit envelope.
ctx.services.database is available only if the host registered a database service through
createToolkit({ services }) and policy granted database.read . Tools with argumentdependent risk add a classify function (section 8.3).

14. Prioritization and release plan
Release planning is gated by the section 20 go/no-go review. If the review re-scopes the product,
P0 changes accordingly.

14.1 P0 — Foundation / MVP
Canonical TypeScript tool contract, JSON Schema validation, per-invocation classification
and typed custom-tool SDK (JSON Schema canonical, Zod helper).
Local runtime, registry, invocation lifecycle, cancellation and structured errors.
Tool selection at package, operation, run and MCP-server level, enforced by the runtime,

Workspace-scoped filesystem tools: read, list, search, glob, grep and diff in the default set;

16. Non-functional requirements
Security: fail closed on missing policy; least privilege; no model-controlled policy overrides;
documented trust boundaries.
Reliability: predictable errors, bounded retries, cancellation and cleanup of child
processes/resources.
Performance: low overhead for schema validation and dispatch; tool execution dominates
end-to-end latency for most integrations. Establish measured budgets after benchmark
baselines.
Portability: support current maintained Node.js LTS releases; macOS and Linux at P0, with
Windows phased in per tool (section 14); publish a per-tool platform matrix.

Context efficiency: each package documents the token footprint of its default tool set;
descriptions stay concise, and footprint regressions are tracked in CI.
Maintainability: strict TypeScript, unit/integration tests, semver, dependency review and
release automation.
Observability: structured logs, traces and metrics with configurable payload capture and
retention.
Usability: first successful tool invocation should be achievable from a small documented
example; errors should explain how to fix configuration safely.
Accessibility: CLI output should be readable without color; docs and generated reports
should use semantic structure.
Privacy: collect no telemetry by default in the open-source local runtime; any optional
telemetry must be opt-in and documented.

20. Competitive landscape, differentiation wedge and go/no-go gate
The space already includes framework-native tool sets, agent SDKs with built-in tools and
permission systems, community and reference MCP servers (filesystem, Git, shell), browser
automation projects, observability platforms, guardrail and policy layers, and sandbox or
execution providers. The product should not compete by claiming the largest list of tools.
Differentiation wedge (hypothesis). A policy-aware execution runtime (capability permissions,
approvals, isolation options, redaction, audit and output shaping) applied consistently across
protocols and frameworks, combined with:
1. One canonical tool contract across MCP and frameworks.
2. A consistent, policy-aware execution lifecycle.
3. Modular, selectable built-in tools and an approachable custom-tool SDK.
4. Tracing, replay and auditability integrated at the runtime layer.
Questions the review must answer.
1. Is there demand for a policy, approval and audit layer that is independent of any one agent
framework or MCP server implementation, and which persona feels the need first?
2. Would a policy-enforcing wrapper around tools the product did not write (for example
external MCP servers) be a stronger, more differentiated product than reimplementing
commodity tools? If so, the MCP client and policy proxy move earlier and the built-in
catalogue shrinks.
3. Which built-in tools are worth owning (those where owning the implementation is needed
to enforce policy) versus integrating from mature libraries?
Go/no-go gate before committing to the P0 build.
A competitor and overlap review across the categories above, dated at the time of review.
Conversations with 5–10 developers matching the primary persona (proposed number),
focused on how they handle permissions, approvals and tool exposure today.
A one-sentence wedge statement that survives both.
Possible outcomes: proceed as scoped; re-scope toward a policy-runtime-first product that wraps
existing tools; or stop. The outcome and its evidence are recorded in this document.

21. Open product decisions
1. Package naming: confirm npm scope, repository name and trademark availability.
2. Runtime direction: recommended hybrid architecture, local-first initial release; validate
demand for hosted remote execution.
3. First framework adapter: MCP is the first adapter (P0). Choose the first framework adapter
based on target-persona usage and API stability, then add further adapters with parity tests.
4. Schema library: proposed: JSON Schema is canonical, with Zod as an authoring
convenience (section 8.3). Confirm in the prototype, including type-inference ergonomics.
5. Sandbox strategy: select platform-specific isolation backends and define exact guarantees
per OS.
6. Search provider: decide whether web search is an adapter interface only or ships with one
default provider.
7. Database support: choose the first supported database and read/write boundary.
8. Telemetry: keep disabled by default; decide whether opt-in anonymous usage metrics are
needed.
9. Licensing: select a license compatible with intended adoption and contribution model.
10. Support policy: define Node.js, OS and framework version support windows.
11. P0 shell scope: proposed: trusted-host only and approval-gated, with a Docker sandbox
backend in P1. Alternatives: pull a container backend into P0, or ship P0 without shell
execution.
12. Approval transport defaults: which approvers ship in P0 (callback and CLI proposed;
webhook/queue and MCP elicitation where feasible) and how non-interactive agents are
configured.
13. Policy-proxy mode: whether the runtime should also wrap tools it did not write (for
example external MCP servers) as a first-class product mode (section 20).
14. Dynamic tool discovery: whether to support deferred loading or tool search after selection
ships (P2).
